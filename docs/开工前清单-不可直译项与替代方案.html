00 / SUMMARY

一页结论

原型是「单屏 306×640 + 14 个 .page 同屏切换 + 1 张 canvas + 5 组内联 SVG + 7 个 DOM 签条 rAF 动画」。小程序的差异不是"样式写法"，而是四层：容器（手机壳/状态栏/胶囊/安全区）、图形载体（无 SVG 元素）、动画载体（无逐帧改 DOM 能力）、字体资产（Android 无 Songti SC）。这四层各有确定的替代方案，但其中 6 处会实质改变实现路径，必须由你定。

一句话：能 1:1 的部分很多，但"顶部状态栏条 + 胶囊"和"签筒 5.6 秒逐帧"这两处，是全项目仅有的两处必须做工程性替代的地方；其余 30 项都是"换载体、不动像素"。

02 / DECISIONS

六项决策：我先给推荐，你确认或改

这六项都会改变实现路径，选错要返工。其余 32 项我按推荐方案执行，你在 §08 一次性过一遍即可。

D1 · 路由模型REC: X3

14 个视图怎么落到小程序页面体系？

  1. X1 全 overlay：1 个壳页 + 14 个视图全做组件。像素最像，但 tabBar 无法自定义到 5 个真实 tab。
  2. X2 全真实路由：5 个 tab 页 + 9 个 navigateTo 页。符合平台习惯，但系统转场（约 250ms 右滑）无法关闭，与原型 pageIn（0.3s 淡入上移 9px）不是一回事。
  3. X3 混合：5 个 tab 用真实页面（强制要求），9 个次级视图（share / intro 1-3 / mt / records / fav / lv / vipbuy）做成全屏 overlay 组件，复用原型的 pageIn .3s。
推荐 X3：tabBar 只能是真实 tab 页；次级页用 overlay 才能 100% 复用 pageIn 与整屏布局。代价：overlay 没有系统返回手势，需内置返回按钮 + 安卓物理返回拦截。
D2 · 比对口径REC: B1

顶部状态栏条与胶囊，怎么算进 2%？

  1. B1 双口径：回归截图时走"基准对齐模式"（nav 固定 41.55px、内容区 598.45px、胶囊区域 mask），另出一份"真机模式"差异作旁证。
  2. B2 只按真机几何：顶部必然下移 16.45px，2% 阈值不可能达标（整页错位）。
推荐 B1。理由：顶部条 306×56 = 17,136px，占整屏 8.7%；刘海机型安全区再占 5.3%——这两块不计入分母，2% 才有意义。报告里会同时标注 mask 面积与原因。
D3 · 支付REC: P1

会员开通（vipbuy）真接微信支付，还是先闭环？

  1. P1 订单闭环 + 支付通道预留：建 orders 集合、云函数下单/回调/查单，前端保留 wx.requestPayment 分支；无商户号时走"沙箱开通"开关。
  2. P2 真支付：需企业主体 + 微信支付商户号 + API 证书 + 回调验签 + 后台发货。任何一环缺失都无法跑通。
推荐 P1。若你已有商户号，直接告诉我，我按 P2 写并在 A6 一起验。
D4 · 大模型REC: M1/M2

签文解读、香语、星语、树洞回响，文案从哪来？

  1. 原型里这些全是硬编码常量（22 条签文库 + 4 组铜钱解读 + 香语/星语模板）。要做到"无假数据"，必须真调模型。
  2. M1 云函数直连：Key 放云函数环境变量，前端不可见。需你提供 provider 与 Key。
  3. M2 云开发 AI 能力：wx.cloud.extend.AI，需在小程序后台开通并配模型。
推荐 M1（可控、可换模型、可加提示词版本号）。请给我：provider（OpenAI 兼容 / 豆包 / 其他）、模型名、Key 存放方式。
D5 · 字体REC: F1

Android 上没有 Songti SC，标题会静默变黑体。

  1. F1 思源宋体子集：按全量文案字符集（去重后约 400–700 字）子集化 woff2，约 60–120KB，托管云存储 https 链接，wx.loadFontFace({global:true}) 启动预载 + 本地缓存 URL。
  2. F2 系统 serif 兜底：Android 多数机型 serif 仍是黑体，不满足"字体不回退"。
推荐 F1。需你确认：允许把字体文件放云存储（会占约 100KB 空间，且首次启动多 300–800ms 等待，我用启动页/骨架屏盖住）。
D6 · 集合口径REC: C1

8 个集合，还是文档里的 13 个？

  1. C1 按 v0.15 §16 的 13 个，统一加 yx_ 前缀：users / sign_daily / asks / favorites / treehole / mutual / rituals / orders / quota / events / config（+ 备份归档）。字段、索引、权限文档里都有。
  2. C2 压成 8 个：今日签、问事、仪式可合并，但查询模式不同（按人按天取一条 / 按人倒序分页 / 按类型取最近 N 条），合并会让索引失效——文档 §16.1 明确反对。
推荐 C1（13 个，带 yx_ 前缀）。"22 个 action"文档里没有清单，我会按 14 视图的实际动作倒推并写成 utils/api.js 常量表，届时给你一份 action 清单复核。

回归方法论里的一个硬事实（先说清，免得后期扯皮）
  1. 2% 不是"任何像素都不许差"，是"结构性差异 ≤2%"。文字抗锯齿（CoreText vs FreeType）必然产生 1px 边缘差异：一行 40 个字、每个字边缘约 30px，合计就可能破 2%。所以 pixelmatch 设 threshold:0.15, includeAA:false，并把"文字边缘"与"结构错位"分开统计。
