01 / SCOPE抽取口径：先把展示壳切出去

原型是“网页里的手机模型”，页面上有一层不属于产品的东西：.phone 手机壳、.screen 内屏框、.hero 深色舞台、.demo-bar / .demo-note / .demo-tip 演示说明、body / h1 / footer 的落地页排版。这些在小程序里没有对应对象（内屏就是真机屏幕），必须整段不搬；否则 WXSS 会带着一套手机边框和演示文案，或者在真机上被裁掉、被压扁。

切分规则写死在脚本里：.phone / .screen / .hero / .demo-bar / .demo-note / .demo-tip / .dv / .kicker / .wrap / .stars / body / h1 / footer 命中即判为 demo，其余为 app。结果是 208 条搬、39 条不搬，逐条可在 tokens.json 的 rules[].scope 里核对。

颜色分三类各自处理：hex 与 rgba 归并为命名 token（屏内 91 个色值全部有名字，零裸色值）；渐变不做 token——渐变是“几何 + 色标”的混合体，拆成 token 反而看不出角度和停止点，A4 时整条内联写、只把色标换成 var()；body 内的 base64 图与 data:image 图标不在颜色统计里（另有 5 个 tab 图标单独走烘焙，见开工清单 NT-07）。

三个非整数陷阱

  1. 1px 边框 → 2.45rpx。真机上 2.45rpx ≈ 1.00px，直接用即可；但若某台机型 DPR 折算后落在半个物理像素，线会“发虚”。处置：先按 2.45rpx 写，真机三机型比对时若发现发虚，再对该处单独换 transform: scaleY() 的 hairline 方案——不预先改，避免大多数机型反而变粗。
  2. 动画位移里的 px 不要转 rpx。签筒 7 根签的 translate 是 rAF 逐帧数学，A5 烘焙 keyframes 时要按 px 采样的比例换算成百分比或 rpx 字面值，两者不能混用，否则位移幅度随屏宽变化。
  3. 字距 letter-spacing 介于字体与布局之间，一律按 px→rpx 转，不保留 px（保留会导致小屏上标题撑行）。

09 / RULES落地规则（写 WXSS 时照这七条）

硬规则

  1. 零裸色值：页面 WXSS 里只允许出现 var(--…)。检验方式是一条脚本：对 miniprogram/pages/**/*.wxss 扫 #hex 与 rgba(，命中即失败。
  2. 字号只从 03 节抄：21 档已在表里，出现表外字号即视为新增设计，需要先改本表。
  3. 长度只用 07 节两列：不要现场心算 k；长度 1 位小数、字号 0.5 取整。
  4. 展示壳样式一条都不搬：.phone / .screen / .hero / .demo-* / body / footer。真机屏幕就是内屏，没有壳。
  5. 渐变内联、阴影取 token：渐变整条写，只换色标；阴影一律 var(--sh-…)。
  6. keyframes 数值写死：不在 keyframes 里用 var() 做插值（iOS 上有已知不稳），变量只用在选择器端的 animation-duration/delay。
  7. 字体三件套：loadFontFace 成功回调后再触发任何 canvas 文字绘制（NT-18），失败则整页落 Songti SC / serif 并在报告里标注。

关于 var() 的可靠性：WXSS 跑在 WKWebView / XWeb 上，自定义属性是支持的；风险只在“变量被用在 keyframes 内部插值”这一处。因此 tokens.wxss 里变量照常声明，但 A5 的签筒 keyframes 一律用字面数值。若真机三机型里真的出现某台机型变量失效（历史上有过 X5 内核老版本），兜底方案是构建期把 var(--x) 就地展开成字面值——tokens.json 里每个 token 都带原值，展开是机械操作，不需要重写样式。
